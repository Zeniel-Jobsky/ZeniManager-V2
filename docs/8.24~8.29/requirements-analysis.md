## 1. 채용공고 추천 기능

### 설명
특정 내담자가 희망하는 직무를 기준으로 채용공고 사이트를 검색하고, 검색된 채용공고를 상담사(또는 내담자)에게 보여주는 기능.

### 목적
- 상담사가 수작업으로 채용 사이트를 검색·스크랩하는 과정을 줄인다.
- 내담자의 희망 직무 데이터(상담 기록에 이미 존재)를 그대로 검색 조건으로 재사용한다.

### 검토 필요 사항
- **검색 대상 사이트**: 어떤 채용공고 사이트(워크넷, 사람인, 잡코리아 등)를 대상으로 할지 확정 필요.
- **연동 방식**: 대상 사이트가 공식 API를 제공하는지, 제공하지 않는다면 크롤링/스크래핑이 필요한지 확인 필요 — 크롤링은 대상 사이트 이용약관 검토가 선행되어야 함.
- **입력 데이터**: 희망 직무 정보를 어느 필드에서 가져올지 (초기 상담 데이터의 어떤 컬럼과 매핑되는지) 확정 필요.
- **결과 표시 위치**: 상담사 화면(내담자 상세)에 탭으로 추가할지, 별도 페이지로 둘지 결정 필요.

### 상태
요구사항 정의 단계. 대상 채용 사이트 및 연동 방식(API/크롤링) 확정 필요.

## 2. 국민취업제도 매뉴얼 검색 기능

### 설명
신입 상담사가 국민취업지원제도 관련 내용이 궁금할 때, AI 에이전트에게 질문하면 답변을 받을 수 있는 기능.

### 목적
- 신입 상담사의 온보딩·교육 부담을 줄인다.
- 제도 매뉴얼/지침을 검색 가능한 형태로 만들어 상담 중 즉시 참고할 수 있게 한다.

### 예상 구조 (RAG 기반)
1. 국민취업지원제도 매뉴얼/지침 문서를 수집한다.
2. 문서를 청크 단위로 분할해 임베딩 후 벡터 DB(또는 Supabase pgvector)에 저장한다.
3. 상담사의 질문을 임베딩해 관련 문서 조각을 검색한다.
4. 검색된 문서를 컨텍스트로 LLM(현재 프로젝트는 OpenAI API 연동 기반)에 전달해 답변을 생성한다.

### 검토 필요 사항
- **원본 데이터 확보**: 매뉴얼 원본(PDF/HWP 등) 확보 및 최신본 관리 주체 확정.
- **저장소 선택**: Supabase pgvector 사용 여부 등 벡터 검색 인프라 결정.
- **UI 위치**: 기존 `CounselChatTab`과 유사한 채팅형 UI로 별도 메뉴에 둘지, 기존 AI 채팅에 통합할지 결정.
- **답변 신뢰성**: 매뉴얼에 없는 내용에 대한 답변 방지(환각 방지) 및 출처(근거 조항) 표시 방식 결정.

### 상태
요구사항 정의 단계. 매뉴얼 원본 확보 및 벡터 검색 인프라 결정 필요.

## 3. 초기 상담 데이터 DB화 기능

### 설명
초기 상담에서 발생하는 정형 데이터와 비정형 데이터(상담 메모, 업로드 문서 등)를 정해진 DB 스키마 형식에 맞춰 자동으로 입력하는 기능.

### 목적
- 상담사가 상담 후 데이터를 수동으로 재입력하는 이중 작업을 없앤다.
- 비정형 상담 기록을 구조화된 데이터로 변환해 이후 통계/분석/유사 사례 매칭에 활용 가능하게 한다.

### 예상 구조
1. 상담 중/후 입력되는 정형 데이터(참여자 기본정보, 희망 직무, 참여 유형 등)와 비정형 데이터(상담 메모, 업로드 문서 텍스트)를 수집한다.
2. 비정형 데이터는 기존 문서 분석 파이프라인(HWP/PDF 텍스트 추출 → LLM 구조화, `client/src/lib/employmentSuccessCase.ts` 등 기존 로직 참고)과 유사한 방식으로 LLM을 통해 정해진 JSON 스키마로 변환한다.
3. 변환된 데이터를 DB 스키마(Supabase 테이블 컬럼)에 매핑해 자동 저장한다.
4. 자동 입력 결과를 상담사가 검수·수정할 수 있는 확인 단계를 둔다.

### 검토 필요 사항
- **대상 DB 스키마 확정**: 초기 상담 데이터가 저장될 테이블/컬럼 구조를 먼저 정의해야 함.
- **정형/비정형 데이터 구분 기준**: 어떤 필드가 정형 입력(폼)이고 어떤 부분이 비정형 텍스트에서 추출되어야 하는지 정의.
- **자동 입력 정확도 검증**: LLM 추출 결과의 오류 가능성이 있으므로, 저장 전 검수 UI 필요.
- **기존 기능과의 관계**: 현재 `Settings.tsx`/`CounselChatTab.tsx` 등에 있는 기존 AI 요약·분석 기능과 파이프라인을 공유할지, 별도로 구축할지 결정.

### 상태
요구사항 정의 단계. DB 스키마 및 정형/비정형 필드 매핑 기준 확정 필요.

## 공통 고려사항

- 세 기능 모두 **AI(LLM) 연동**이 필요하며, 현재 프로젝트는 OpenAI API 키를 사용자가 앱 내 설정 화면에서 직접 입력하는 구조([client/src/lib/supabase.ts](../../client/src/lib/supabase.ts))를 따르고 있어, 신규 기능도 동일한 키 관리 방식을 따를지 검토 필요.
- 외부 사이트 연동(1번) 및 외부 문서 수집(2번)은 법적/약관 검토가 선행되어야 한다.
- 세 기능 모두 상담사 검수(휴먼 인 더 루프) 단계를 두어, AI 결과를 그대로 신뢰하지 않고 최종 확인 후 반영하는 흐름을 기본으로 한다.
